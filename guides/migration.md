# 迁移与故障处理

## 从 GitHub Pages 搬到自己的服务器

先保留完整源码、content/posts 和锁文件。普通静态服务器只需要构建产物，不需要安装 Node.js 来处理读者请求。

1. 在 site.config.ts 设置新的 origin 与 base。根目录是 /，子目录例如 /notes/。
2. 运行 pnpm install --frozen-lockfile 与 pnpm build。
3. 将 docs/.vitepress/dist/ 的全部内容放到对应静态目录。
4. 检查首页、文章直接打开/刷新、搜索、图片、原 PDF、写作页与 PDF 导入。

文章地址保留 .html 后缀，每个页面都有实际文件。无需单页应用 fallback，也不应把所有未知路径强制指向首页。错误路径应该返回 404。服务器需提供正确的 JS、CSS、PDF 与 WebAssembly MIME 类型，PDF worker 是本地 .mjs 文件。[VitePress 部署](https://vitepress.dev/guide/deploy)、[资源与 base](https://vitepress.dev/guide/asset-handling)

域名或 base 改变后需要重新构建。内容中的图片路径仍是 assets/…，无需逐篇修改。Markdown 文章和资源可以交给其他生成器；自定义首页、搜索和写作台源码需要单独移植。

当前作者保存目标仍是 GitHub。只搬读者站点不会改变这一点。如果未来连内容存储也要搬走，可以替换 src/core/github.ts 所在的存储适配流程，或者继续用文章包和本地 Git。浏览器草稿按网址隔离，搬迁前先下载备份，之后在新站点导入。

## 日常本地发布

把下载的文章 ZIP 解压为 content/posts/文章地址/index.md 和 assets/。运行 pnpm check，再用你自己的版本管理流程提交文章和资源。相应 GitHub 分支收到提交后会触发工作流。不要只提交 Markdown 而漏掉图片。

如果 GitHub API 不可用，文章包仍能用于本地备份和构建。站点无需改成带后端的应用。

## 常见问题

**本地页面能开，部署后样式或图片丢失。** 检查 base 是否对应实际托管位置。项目 Pages 通常需要 /仓库名/。重新构建后上传全部产物，不能只替换首页 HTML。

**搜索没有更新。** 搜索索引在构建时由正文生成。先确认最新提交的工作流成功，再检查浏览器缓存。

**导入图片显示缺失。** 单个 Markdown 不包含图片数据。导入图片所在的整个文件夹或 ZIP，保留目录层次；不要把本机 C:\... 绝对路径写进文章。外链图片需要先保存为本地资源。

**草稿没有恢复。** 确认使用了原浏览器和原网址，包括协议、域名和端口。若清理了网站数据，只能从文章包或已发布仓库恢复。未保存成功时界面会提示，不会将失败标成已保存。

**PDF 中中文或排版不对。** PDF 的文字编码、字体或列布局可能无法可靠还原。打开原文件比较，编辑草稿，或勾选仅保留原 PDF 后重新导入。不要把转换结果直接当作完整原文。

**没有 pnpm。** 安装 Node.js 24 后，可按 pnpm 官方方式安装 10.30.3。构建使用锁文件，避免自行改用另一个包管理器生成不同版本。

**Windows 构建工具提示权限错误。** 使用具有项目目录正常读写权限的终端运行。不要修改系统代理或安全策略来掩盖错误。交付机器中的受限执行环境需要对本地构建进程授权，这不是项目需要管理员权限的设计。

**工作流成功但界面还未显示部署完成。** 检查匹配该提交的 Pages 部署记录、环境审批以及 token 的 Deployments 读取权限。内容保存与部署是两个阶段，等待或刷新不会丢掉已提交内容。
